## FIX 1 — Set quantity shows wrong ("Set" / "44 Sets")

### Root cause
- Tablet writes `pax = numSets × 22` into the booking:
  - `Tablet_PWA/frontend/js/wizard.js:1484` → `d.event.pax = (d.event.numSets || 1) * 22;`
  - `Tablet_PWA/frontend/js/wizard.js:1831` → same
  - `Tablet_PWA/frontend/js/wizard.js:1130` → `d.event.pax = newTotal * 22;`
  - Android twins: `.../assets/js/wizard.js:1484, 1831, 1130` (+ `:1913`, `:2038`)
  - Payload sends both `pax: 44` and the correct `num_sets: 2` (wizard.js:3092-3093).
- Renderers then print `pax` with a "Set(s)" suffix instead of `num_sets`:
  - Tablet PDF: `Tablet_PWA/frontend/js/exporter.js:401` → `Quantity: ${pax} Set(s)` (prints 44). (Line 353-354 already prefers `num_sets` — inconsistent.)
  - Desktop agreement PDF: `Catering_Present/jayraldines_catering/utils/exporter.py:851` (`pax = ... or "—"`), `:865-866` (`"No. of Sets:" → f"{pax} Set(s)"`), `:1113` (package card), `:1258/1264-1266` (invoice renderer).
  - Desktop kitchen slip: `components/order_print_dialog.py:580` (`pax` default 100), `:584`, `:665-666`.
  - The genuine `No. of Sets` row is **suppressed for food sets**: `order_print_dialog.py:971`.

### Changes
1. **Stop deriving the displayed Set count from `pax`.** In every renderer, when the booking is a food set, show `num_sets` (fallback `sets[].quantity` total), NOT `pax`:
   - `Tablet_PWA/frontend/js/exporter.js:401` and Android twin → use `numSets` (already computed at line 342) instead of `pax`.
   - `utils/exporter.py:865-866`, `:1113`, `:1264-1266` → use a `num_sets` value for the "Set(s)" figure; keep `pax` only for non-set (Pax) bookings.
   - `components/order_print_dialog.py:580-666` → use `num_sets` for the SET strip value.
   - `order_print_dialog.py:971` → stop suppressing the `No. of Sets` row for food sets (it is the correct quantity to show).
2. **Decide what `pax` means for a set booking** (pick one, confirm with client):
   - Option A (recommended): keep `pax` as the real guest headcount the user entered, and show Set count separately from `num_sets`. Requires the tablet to stop overwriting `pax = numSets × 22`.
   - Option B: keep auto-computing total guests but never label it "Set(s)".
3. **Remove the `× 22` auto-compute** (ties into Fix 4): `wizard.js:1130, 1484, 1831` (+ android `:1913, :2038`). Replace with either a user-entered pax, or the package's real `min_pax` / per-set guest value from the package record — never a hardcoded 22.
4. **Guard the breakdown fallback:** `order_print_dialog.py:542-548` defaults missing `quantity` to 1 and skips entirely when `sets` is empty — ensure `num_sets` round-trips so the breakdown is never empty for a set booking.

### Verify
- Create a booking with 2 sets on the tablet → receipt/slip and desktop agreement PDF all read **"2 Set(s)"**, never 44, never blank.
- Create 1 set and 5 sets → shows 1 and 5.
- A non-set (pax) booking still shows the correct "No. of Pax".

## FIX 2 — Tablet delete crashes the desktop server (CRITICAL)

### Root cause (verified)
Native SQLite access violation from a cross-thread finalization race:
- `utils/db_sync_server.py:2728` uses `ThreadingHTTPServer` → **one new thread per HTTP request** (`daemon_threads=True`).
- `utils/db.py:224-229` opens the shared connection with `check_same_thread=False` (safety guard disabled), WAL, `isolation_level=None`.
- `utils/db.py:317-343` — worker threads lazily open their **own** thread-local read connection; **never closed** when the request thread dies (`db.py:2396-2401` only closes the current thread's conn).
- `utils/db.py:1303-1316` — on worker threads, `fetchall` runs under `nullcontext()` (**no lock**); the crash site is the `[dict(r) for r in rows]` listcomp (`db.py:1313-1314`) which triggers a GC pass.
- Sequence: a delete runs writes under `_db_lock` (and WAL checkpoint), while concurrent `/api/db/snapshot` (`db_sync_server.py:1330-1336`) and `/api/lan/sync` (`perform_server_sync` `:2190`, `:2199`; PIL thumbnails `:134-138`) read on unlocked leaked connections. GC finalizes a dead thread's `sqlite3.Connection` (native `sqlite3_close`) mid-`sqlite3_step` on another thread → **access violation**.

### Changes (pick the combination; 1+2 are the core fix)
1. **Serialize all SQLite access through one lock**, or give the sync server a single dedicated serialized DB worker/queue. Minimum: make worker-thread reads in `db.fetchall`/`db.fetchone` (`db.py:1303-1316`, `:1370`) acquire `_db_lock` too — remove the `nullcontext()` fast path so reads and the delete writer can't run concurrently with WAL checkpoints.
2. **Deterministically close per-thread connections** when a request finishes, instead of leaking them to GC. Options:
   - Close `_tls.read_conn` at the end of each `do_GET`/`do_POST` (finally block), or
   - Replace thread-local connections with a small bounded connection pool with explicit checkout/return and `close()` on return.
3. **Avoid GC tearing down connections on arbitrary threads:** keep a reference / explicit lifecycle so `sqlite3_close` only runs on the owning thread while no query is in flight.
4. **Lower allocation/GC pressure on the hot path** (secondary): the snapshot and `perform_server_sync` build large lists + PIL thumbnails per request. Consider caching/throttling the snapshot and the `_image_to_data_uri` results so a delete doesn't coincide with a heavy allocation burst.
5. **Last-resort safety net:** wrap `serve_forever`/handlers so a native-level failure can't take the GUI process down silently, and ensure the server thread restarts cleanly. (Does not fix the root cause — do 1-3 as well.)

### Verify
- Delete many bookings from the tablet in quick succession while the desktop is also loading reports/calendar/notifications → no crash, no `crash_traces.log` access violation.
- Confirm `app_*.log` shows "Processed tablet deletion" with **no** session restart immediately after.
- Stress: concurrent snapshot + sync + delete in a loop.

## FIX 3 — Replace delete browser-dialog with slide-to-confirm (tablet)

### Current state
Booking deletes use native `confirm()`:
- `Tablet_PWA/frontend/js/wizard.js:3682` (calendar day-preview delete) + Android twin
- `Tablet_PWA/frontend/js/settings.js:532` (bookings list `[data-delete-booking]`) + twin
- `Tablet_PWA/frontend/js/settings.js:705` (booking detail modal `#modal-delete-booking-btn`) + twin

No slide-to-confirm widget exists. Best reusable pattern: swipe-to-remove in `wizard.js:303` (`wireCartSwipeToRemove` / `attachSwipeRow`, lines 306-449; threshold at `:392`) with CSS at `css/styles.css:5011` and `:5083`.

### Changes
1. Build a reusable **slide-to-confirm** control (e.g. `slideToConfirm({label, onConfirm})`) modeled on the `wizard.js:303` drag+threshold logic (touch + mouse/pointer), returning a Promise that resolves on commit.
2. Replace the three booking `confirm()` call sites (wizard.js:3682, settings.js:532, settings.js:705) with the slider, shown inside the existing modal/sheet UI — **no browser dialog**.
3. Add matching CSS (reuse/extend the swipe-to-remove styles at `styles.css:5011`).
4. Apply identically to the Android asset copies (same line numbers).
5. (Optional) convert the other non-booking `confirm()` deletes for consistency — out of scope unless client asks.

### Verify
- On the tablet, deleting a booking shows a slide-to-confirm (not a browser popup); partial slide cancels; full slide deletes and syncs.
- Works with touch and with mouse; works on both PWA and Android build.

## FIX 4 — Remove hardcoded "good for 22 persons"

### Locations (verified)
Tablet (PWA + Android twins, same line numbers):
- `js/wizard.js:1539` — "1 Set is good for 22 persons (4 dishes)..."
- `js/wizard.js:1649` — pill "Min 1 Set (4 dishes good for 22 person)"
- `js/wizard.js:1965` — "1 Set is good for 22 persons (4 dishes). Minimum order: 1 set."
- `js/app.js:381` — pill "Min 1 Set (4 dishes good for 22 person)"
- `js/app.js:1189` — same pill (absolute-positioned)
- Plus the `× 22` compute at `wizard.js:1130, 1484, 1831` (android also `:1913, :2038`) — see Fix 1.

Desktop:
- `components/search_dropdown.py:193` — `"sub": "Min 1 Set (4 dishes good for 22 person)"`
- `components/booking_modal.py:1007` — fallback "Min set: 1 Set (4 dishes good for 22 person)"
- `components/booking_modal.py:1385` — `f"Min: {pkg.get('min_pax', 1)} set (good for 22 pax)"`

> Leave alone (unrelated "good for 3 hours" service duration): `terms.js:19`, `terms.js:77`.

### Changes
1. Delete the hardcoded "good for 22 person(s)" text from all 5 tablet spots and 3 desktop spots.
2. Where a per-set capacity genuinely needs to be shown, read it from the **package record** (e.g. `pkg.min_pax` / a real per-set guest field) instead of the literal 22. If the package has no such value, show nothing (do not assume).
3. Remove the `× 22` multiplier (shared with Fix 1) so no "22" leaks into `pax`.

### Verify
- Package/wizard screens no longer display "22" anywhere the client didn't enter it.
- A package with no capacity set shows no fabricated number.
